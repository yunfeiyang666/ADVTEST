### 📝 课题核心思想备忘录（关于QATest和课题框架目的）





#### 1. `QATest` 论文的本质与局限



你通过精读 Introduction，准确地识别出了传统 QA 测试的两大痛点，而 `QATest` 提供了针对性的解决方案：

- **痛点1：Oracle 难题（答案不唯一）**
  - *问题：* 问答系统的答案可能不是确定性的（比如一个问题有多个合理答案），导致无法定义“标准答案”。
  - *QATest 方案：* 采用“蜕变测试”（Metamorphic Testing）。它不关心答案 *是* 什么，只关心答案 *是否一致*。它通过“文本算子”（如 `what is` -> `what's`）生成语义一致的问题，并**期望模型的答案保持不变**。
- **痛点2：Fuzzing 效率难题（盲目测试）**
  - *问题：* 以前的方法缺乏“测试指导和选择策略”，导致生成大量“冗余或无效测试”。
  - *QATest 方案：* 提出两大“测试指导”标准：
    1. **`N-Gram 覆盖率`**：保证**语言多样性**（避免重复问同一种句式）。
    2. **`困惑度优先级`**：保证**语言质量**（避免生成语法不通的废话）。



#### 2. 我们的核心创新：从“语言”走向“安全”



我们深入讨论后一致认为，`QATest` 框架虽好，但它只是一个“**文本 Fuzzer**”。在“自动驾驶安全”这个产业命题上，它有两大“致命缺陷”，而我们的项目正是为了解决这两个缺陷：

- **缺陷一：`QATest` 缺乏“语义覆盖”（只测了“语言鲁棒性”）**
  - *`QATest` 的局限：* 它的 `N-Gram` 指导 只关心“句式”，不关心“考点”。如果“种子集”里没问过“交通锥桶”，`QATest` 永远也“发明”不出关于“锥桶”的问题。
  - *我们的创新 (来自 S3C)：* 引入**“场景图覆盖率”**。我们不再局限于“种子集”，而是直接分析图像本身，确保场景中的**所有“事实”（如 `(锥桶, left_of, 自车)`)** 都能被测试到。
  - *实现方式：* 正如你所预判的，我们通过“**基于模板的生成**”（如 `NuScenes-QA` 论文 所示），并结合**“人机协同”**（专家定义关键模板，LLM 负责统计和多样性） 来自动生成新的“考点”问题。
- **缺陷二：`QATest` 缺乏“视觉覆盖”（只测了“耳朵”，忘了“眼睛”）**
  - *`QATest` 的局限：* 它的所有算子（MRs） 都是**“改问题”**（文本）。
  - *我们的创新 (来自 PPT)：* 引入**“视觉蜕变算子”**。我们**“改图片”**（如 `晴天` -> `雨天`），然后问**同一个问题**，看模型的“视觉鲁棒性”是否过关。



#### 3. 我们的“升华点”：新问题与新价值



结合上述两点创新，我们发现了比 `QATest` 更深层次的问题和价值：

- **【已存档】创新点 1：混合指导策略 (Hybrid Guidance)**
  - *新问题：* 我们同时拥有了两个竞争的测试目标：`N-Gram 覆盖`（语言新颖度）和 `S3C 覆盖`（场景新颖度）。
  - *我们的创新：* 设计一个“**多目标调度算法**”来智能地分配测试资源（例如：S3C 优先发现新考点，QATest 立即跟进生成文本变体）。
- **【已存档】创新点 2：量化“自动驾驶安全”**
  - *新价值：* 我们的最终目的**不是测“语言模型”**。
  - *我们的目标是：* **“量化 VLM 对高风险驾驶场景（Corner Cases）的覆盖程度”**。
  - *最终产出：* 不是一个笼统的 `20%` 精度，而是一张**“安全风险雷达图”**（如：`雨天-行人` 场景精度 15%）。



#### 4. 项目“本质”澄清（我们的角色）



我们最后明确了项目的本质，解决了你的“迷失感”：

- **我们的工作（Fuzzing 循环）：** 我们的本质是构建一个“**Bug 发现雷达**”。我们通过“生成”（QATest+S3C+视觉）和“量化”（混合指导+覆盖率），产出一份**“高质量的 Bug 报告”**。
- **开发者的工作（MLOps 循环）：** 开发者拿走我们的“Bug 报告”，去**“加强对大模型的训练”**。













### 📝 议题备忘录：客观评价 QATest 的贡献与局限





#### 1. 核心议题



你提出了一个关键的观察：`QATest` 所谓的“通用性” 1 似乎**并没有**解决测试集**“多样性”**（Semantic Diversity，即新的“考点”）的根本问题，而更像是对“同义变换”（Linguistic Robustness）操作的规范化和效率提升。





#### 2. 客观分析：`QATest` 论文的真实贡献



我们的分析确认，`QATest` 的核心贡献是**“工程效率”**和**“标准化”**，而非“语义创新”。

1. **贡献一：统一性 (Uniformity)**

   - 它提供了**第一个**能够**统一**测试 `MRC`、`KBQA`、`ODQA` 等不同架构 2222的框架，解决了此前测试工具（如 `MT4MRC` 3）只能测 `YES/NO` 4 问答的局限性。

     

     

2. **贡献二：效率 (Efficiency)**

   - 它**首次**引入了“**测试指导**”（Testing Guidance） 的概念，解决了此前方法“盲目生成”导致的“大量冗余或无效测试” 的问题。
   - 它使用的 `N-Gram 覆盖率` 和 `困惑度优先级` 指标，其**唯一目的**是优化“种子库” 的**“语言多样性”**（剔除无效句式，奖励新颖句式）。



#### 3. `QATest` 的根本局限（你的观察是对的）



我们共同确认了 `QATest` 的一个根本局限：

- **无法创造“新知识”：** `QATest` 100% 受限于“种子集”的语义范围。
- **举例：** 如果“种子集”里只有关于“车”的问题，`QATest` 无法通过“同义变换”“发明”出一个关于“交通锥桶”的新问题。
- **结论：** `QATest` 只能测试**“语言鲁棒性”**（Linguistic Robustness），而**不能**测试**“语义多样性”**（Semantic Diversity）。



#### 4. 对我们项目的启示（为什么我们的创新是必要的）



这个局限性**客观上**证明了你的 PPT 中引入 `S3C` 的**必要性**：

- 在“自动驾驶安全”领域，“语义多样性”（即覆盖**致命的 Corner Case**）远比“语言鲁棒性”（不认识 `what's`）更重要。
- `QATest` 解决了“如何高效地问”的问题。
- `S3C`（场景图覆盖） 解决了“**该问哪些新问题**”的难题。
- 因此，我们的项目（`QATest` + `S3C`）是一个**互补的、完整的**测试方案。

### 📝 议题备忘录：可解释性 (Explainability)





#### 1. 概念一：“解释性回答”（来自被测模型 SUT）



- **这是什么？**
  - 这不是 `QATest` 论文的原理。
  - 这是**被测模型（SUT）**（如 `Qwen2-VL`） 自身的**特性**。
- **原理：**
  - `Qwen2-VL` 是**生成式 AI**（Generative AI）。
  - 它的训练目标是“像人一样对话”，因此当你提问时，它默认会生成一段通顺的、带有“原因解释”的句子，而不是像老模型那样只输出 `yes` 或 `no`。
- **对我们的影响（负面）：**
  - 这种“解释性回答”恰恰是导致我们昨天跑出 **20% 低分 的主要原因**。
  - 我们的自动判分脚本（`eval_task4.py`） 期望一个关键词（如 `yes`），但模型给了一句解释（如 "There are no visible pedestrians..."），导致“判错”。



#### 2. 概念二：“可解释性报告”（来自我们的框架）



这是我们为了**弥补 `QATest`“黑盒”缺陷**而设计的**项目创新点**。`QATest` 只能告诉你 `FAIL`，而我们的框架能告诉你 `WHY FAIL`。

- **这是什么技术？**

  - 这不是 AI 技术，而是一种高效的软件工程设计模式：**“元数据标记”（Metadata Tagging）**。

- **原理：**

  - 我们的框架（Fuzzer）在生成测试用例时，**不仅仅**是生成一个“问题字符串”。
  - 它会生成一个“**带标签的测试对象**”（如 JSON），这个对象里包含了“问题”以及描述其“出身”和“目的”的**元数据标签**。

- **示例标签：**

  - 来自 QATest 的算子：

    { "question": "what's car", "source_mr": "QATest.MR2.Abbreviation" }

  - 来自 S3C 的算子：

    { "question": "How many traffic cones?", "source_mr": "S3C.Counting.TrafficCone" }

- **如何实现“可解释性”？**

  - 当 `eval_task4.py` 跑完所有测试后，我们不再只有一个 `20%` 的总分。

  - 我们可以对所有 `FAIL` 的测试用例，按它们的 **`source_mr` 标签**进行**分组统计（Group By）**。

  - 最终产出（可解释的报告）：

    “测试失败报告：在 S3C.Counting.TrafficCone（数锥桶） 类别上失败了 850 次；在 QATest.MR2.Abbreviation（缩写） 类别上失败了 5 次。”

  - 这就是我们（PPT）的框架如何弥补 `QATest` “缺乏可解释性”缺陷的方法。
